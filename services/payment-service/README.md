# Payment Service

FastAPI + PostgreSQL + Kafka. Takes payment for orders, once per idempotency key, and
announces the outcome as `PaymentProcessed` or `PaymentFailed`.

Full API and event reference: [`docs/api/payment-service.md`](../../docs/api/payment-service.md).

## Layout

```
app/
  main.py          FastAPI app, domain-error -> HTTP mapping
  consumer.py      the OrderCreated consumer process (python -m app.consumer); the only
                   module that builds aiokafka clients
  core/            settings, logging
  db/              engine, session, declarative base (with a constraint naming convention)
  models/          SQLAlchemy ORM models and the payment state table (private to this service)
  schemas/         Pydantic request/response contracts (the public API)
  repositories/    the only layer that writes SQL; never commits behind the caller's back
  services/        business rules; knows nothing about HTTP or Kafka
  providers/       the PaymentProvider protocol and the deterministic fake
  messaging/       envelope and event models, the OrderCreated handler, publisher,
                   retry and dead-letter logic
  api/v1/          routes
alembic/           migrations (the schema's only source)
tests/             pytest suite; SQLite and fakes, no Postgres or Kafka needed
```

One image, two processes: the API (`uvicorn app.main:app`) and the consumer
(`python -m app.consumer`). They share the service and repository layers, so a payment
taken over HTTP and one taken from an `OrderCreated` event follow the same rules.

## Run it

With Docker Compose, from the repository root:

```bash
docker compose up --build payment-service payment-consumer
```

The API container runs `alembic upgrade head` before it starts uvicorn, so the schema is
always current. The consumer waits for it to be healthy.

Without Docker (SQLite, no Postgres needed; the consumer needs a broker on `localhost:29092`):

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt   # Windows
# source .venv/bin/activate && pip install -r requirements-dev.txt  # macOS/Linux

cp .env.example .env
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8083
.venv/Scripts/python.exe -m app.consumer          # in a second terminal
```

Then open <http://localhost:8083/docs>.

## Migrations

```bash
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m alembic revision --autogenerate -m "describe the change"
.venv/Scripts/python.exe -m alembic downgrade -1
```

`alembic/env.py` reads the URL from `PAYMENT_SERVICE_DATABASE_URL`, so the migrations
always target the service's own database. Review every autogenerated file before
committing it: autogenerate renders server defaults for the database it compared against
(SQLite's `CURRENT_TIMESTAMP`), and misses renames entirely. `tests/test_migrations.py`
fails if the models and migrations drift apart.

## Tests and linting

```bash
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m ruff check app tests
.venv/Scripts/python.exe -m ruff format app tests
```

90 tests. They use SQLite (in memory, or a temporary file for the migration tests) and
fakes for the payment provider, Kafka consumer and producer, so they need no Postgres and
no broker. `test_event_wire_shape.py` runs `scripts/validate-event-schemas.py` over the
events exactly as the publisher serialises them.

## Configuration

All settings are environment variables prefixed `PAYMENT_SERVICE_`; see
[`.env.example`](.env.example).

| Variable | Default | Purpose |
|---|---|---|
| `PAYMENT_SERVICE_DATABASE_URL` | `sqlite+pysqlite:///./payment_service.db` | SQLAlchemy URL, used by the app and Alembic |
| `PAYMENT_SERVICE_LOG_LEVEL` | `INFO` | |
| `PAYMENT_SERVICE_PAYMENT_PROVIDER` | `fake` | Which provider to charge through; only `fake` exists |
| `PAYMENT_SERVICE_FAKE_DECLINE_ABOVE` | `1000.00` | The fake declines any amount above this with `card_declined` |
| `PAYMENT_SERVICE_KAFKA_BOOTSTRAP_SERVERS` | `localhost:29092` | `kafka:9092` inside Compose |
| `PAYMENT_SERVICE_KAFKA_ORDERS_TOPIC` | `orders` | Consumed |
| `PAYMENT_SERVICE_KAFKA_PAYMENTS_TOPIC` | `payments` | Produced |
| `PAYMENT_SERVICE_KAFKA_GROUP_ID` | `payment-service` | Consumer group |
| `PAYMENT_SERVICE_KAFKA_MAX_ATTEMPTS` | `3` | Attempts in total before a message is dead-lettered |
| `PAYMENT_SERVICE_KAFKA_RETRY_BACKOFF_SECONDS` | `0.5` | Linear backoff base between attempts |
| `PAYMENT_SERVICE_PROCESSED_EVENTS_RETENTION_DAYS` | `8` | Topic retention (7 days) plus a margin |
| `PAYMENT_SERVICE_PROCESSED_EVENTS_PRUNE_INTERVAL_SECONDS` | `3600` | How often the consumer prunes |
